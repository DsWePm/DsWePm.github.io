## 这一篇要学什么

读完这一篇，应当能够：

1. 说出集成要解决的几个问题：由谁来开，什么时候换，换的时候接口怎样保持一致；
2. 解释“迟滞”（进入和退出用不同的门槛）的作用，并能用几行伪代码写出切换规则；
3. 说明“证明另一条线不存在”和“没有看到另一条线”的区别；
4. 说出开环回放怎样证明集成后的代码与车上测过的代码一致，以及它不能证明什么。

> 重点：根据看到的内容选控制器；迟滞；热备；接口对齐；开环回放。
>
> 难点：“没看到”不等于“不存在”；各模块单独验证过，放到同一个节拍下运行，还会出现新的差异。

预备知识：前三篇。

## 先看一个问题

小车要开的路有三种样子：先是两侧都有锥桶的双侧路，路中间会有板子；接着变成只有一侧有锥桶的单侧路；最后在路的尽头要倒车入库，停进一个 U 形车位。每一种样子各有一个控制器：双侧用 PPO，单侧用前两篇讲的 SAC 加 PID，停车有专门的停车模块。它们各自在仿真和实车上调好了。

把它们放进同一个程序，让车从头开到尾，还有三个问题要回答：现在该由谁来开？什么时候换？换的时候，各个控制器输出的命令接不接得上？每个控制器单独好用，并不等于它们能稳定地来回切换。

这一篇讲这条集成链是怎么做的，以及集成中遇到的问题。双侧的 PPO 和停车模块作为现成的组件接入。集成工作本身包括单侧的 SAC 加 PID、第一版集成链，以及后来对单位、检查宽度和丢路交接的对齐。

先认几个词。

| 名称 | 意思 |
| --- | --- |
| ROS、节点 | ROS 是机器人常用的软件框架，节点是其中一个独立运行的程序。这里整条链是一个节点 |
| 发布者 | 把命令发给车辆接口的那一部分。整个节点只有一个 |
| PPO | 一种强化学习算法。这里用它训练出来的控制器负责双侧路 |
| MPC | 模型预测控制：先用车辆模型向前预测，再选出最优的动作。这里只在对比和备选中出现 |
| 迟滞 | 进入和退出一个状态用不同的门槛，防止在临界点附近来回切换 |
| 热备 | 当前不在场的控制器继续运行、输出不用，切换时不必重新启动 |
| 开环回放 | 把记录下来的输入逐帧交给被测代码，比较输出。输出不会影响下一帧的输入 |

## 一个节点，一个发布者

整条链在一个节点里运行。每一帧，它根据车看到的东西，选出当前该用哪个控制器。各控制器输出的命令，在输出之前只做一次单位对齐，由唯一的一个发布者发给车辆。

![一个节点、一个发布者：车每一帧根据自己看到的东西选控制器。双侧 PPO、单侧 SAC 加 PID、停车各自保留它们上车测过的设置；不在场的道路控制器保持热备，输出不用；输出前单位只对齐一次。每个控制器保留自己的设置，只有接口（单位、交接、停车规则）是共用的。](notes/chain-integration-switching/chain.svg)

节拍方面：整个节点每收到一帧激光雷达数据（约每 0.1 s 一次）运行一步。PPO 保持原来的做法，只在有新的相机帧时更新，其余时间保持上一条命令。后面有一节专门讲触发方式。

## 根据看到的内容选控制器

最直观的做法是“跑了多少米就切换”。但这要知道每段路的长度，场地一变就全错。这条链每一帧只根据传感器看到的东西来选择，不依赖路段长度和里程。

| 切换 | 条件 | 为什么这样定 |
| --- | --- | --- |
| 双侧 → 单侧 | 在“另一条线确实不存在”的证据下，累计行驶 1 m | 弯道里和绕板时，另一条线只是在视野之外 |
| 单侧 → 双侧 | 两条线都看到（每条至少 2 个本车道的锥桶），连续 3 个相机帧 | 3 帧可以滤掉一次偶然的看见，转向不会跳变 |
| 道路 → 停车 | 车位在连续 3 次雷达扫描里被确认；或者路断 1 s（视野里没有锥桶，或单侧控制器没有路） | 锥桶线在车位处结束 |
| 停车 → 道路 | 车位还没有锁定时，本车道的锥桶连续 3 帧又出现 | 路中间缺了一段锥桶，不能就此停车 |
| 备用基线 | 只在确认可走的路上，指令无效或车无故不动超过 3 s | 它没有激光绕障能力，不能随便接管 |

## 证据和迟滞

先看一个问题：只看到一条线，能不能说明另一条线不存在？不能。弯道里另一条线会跑出相机的视野，绕板时锥桶会被挡住，这两种情况下相机都“只看到一侧”，路其实还是双侧的。

所以这条链不去数“看到了几条线”，而是去证明“另一条线确实不存在”。办法是：把看到的那条线按车道宽度平移，推算另一条线应该在哪里。同时满足下面两个条件，才算“确实不存在”：

- 推算出的点至少有 3 个落在相机的视野内（±30° 以内，距离 0.5 m 到 3 m）；
- 这些点附近没有另一种颜色的锥桶。

弯道里和绕板时，推算点落在视野之外，就记为“没有证据”：既不支持“存在”，也不支持“不存在”。

这个判据的效果，用 64 次非停车的实车运行记录来比较。直接用共享观测里的“单侧”标志来判断，误判持续最长的一次有 11.3 m（其余也有 3 到 5 m）。用上面这个证据判据，最长只有 0.7 m。

有了可靠的证据，还要防止来回抖动。办法是迟滞，也就是进入和退出使用不同的门槛。

- 进入单侧：累计 1 m 的“另一条线不存在”的证据。“不存在”是推断出来的，容易看错，所以要求多一些。
- 回到双侧：只要连续 3 帧两条线都在。“看到了两条线”是直接的观察，可靠，所以要求少一些。

规则可以写成下面的伪代码（示意）：

```text
累计距离 = 0；连续帧数 = 0
每个相机帧：
    如果 两条线都看到：
        累计距离 = 0；连续帧数 = 连续帧数 + 1
    否则如果 另一条线被证明不存在：
        累计距离 = 累计距离 + 本帧行驶的距离；连续帧数 = 0
    否则（没有证据）：
        累计距离不变；连续帧数 = 0
如果 现在是双侧控制，并且 累计距离 ≥ 1 m：换成单侧控制
如果 现在是单侧控制，并且 连续帧数 ≥ 3：换回双侧控制
```

规则里还有几个细节要记住。累计的是行驶距离，不是帧数：没有证据的帧，计数保持不变，只有看到两条线才清零。进和出的门槛不同，理由见上。停车的接管也不是一次性的承诺：在车位锁定以前，它只是“试探”，如果连续 3 个相机帧又看到本车道的锥桶，就退回到道路控制器，“没找到车位”而中止之后也一样；车位锁定以后才不再退回。

下图把规则里的常量（1 m、3 帧）放在一段脚本化的证据流上运行（示意：证据流是人为构造的，规则和常量取自实际代码），并和“每一帧都按最新证据切换”的做法比较。

![切换迟滞（示意）。最上面的色带是脚本化的相机证据流：绿色是看到两条线，橙色是只看到一条线且另一条被证明不存在，灰色是没有证据。往下两行：在“一条线”证据下累计的行驶距离（只有两条线出现时才清零，到 1 m 才切到单侧），和连续看到两条线的帧数（到 3 帧才切回双侧）。最下面两条色带是控制器的选择：用 1 m、3 帧的迟滞一共只切换了 2 次，“按最后一帧切换”的做法切换了 14 次。](notes/chain-integration-switching/switch.gif)

车位本身也要“像个车位”。长度超过 2.2 m 的，不是真的车位。车位开口处连续 3 个相机帧看到锥桶，说明它在锥桶线的后面，也不是。这两种情况都要丢弃已建的车位地图，重新建。

## 不在场的控制器保持热备

双侧用 PPO 开，单侧换成 SAC 加 PID 时，PPO 并没有被关掉。它每一帧仍在计算，只是输出不用，这就是热备。这样切回来的那一刻，PPO 的锥桶滤波、道路记忆和它自己的观测程序都是最新的，不需要重新启动。切换时，转向从车上此刻的值接续，不会在切换的那一帧里突然跳变。反过来，切到单侧控制器时，PID、绕障规则、速度上限和适配器的内部状态都要复位，让它们从干净的状态开始。

下面是代码节选（做了简化）：

```python
# 单侧控制器开车时，PPO 仍在后台走一步，滤波、记忆和观测程序保持最新
...
elif self.stage == 'SINGLE' and self.double_frames >= self.DOUBLE_EVIDENCE_FRAMES:
    self.stage = 'DOUBLE_PPO'      # 换回双侧
    self.single_m = 0.0            # 单侧证据的累计距离清零
    o = self.ppo.s
    self.ppo.applied = output[1] / (o['steer_sign'] * o['steering_scale'])   # 从车上当前的转向接续
    self.ppo.steer = max(-1.0, min(1.0, self.ppo.applied))
```

## 接口要一次对齐

所有控制器看的是同一份 18 个数，但这不等于它们可以互换：同样的输入，不同控制器输出的“命令”含义并不一样。

| 控制器 | 输出的是什么 | 怎样处理 |
| --- | --- | --- |
| PPO | 车端的单位：转向符号、±1.0 的范围、速度控制、刹车 | 绕过单侧控制器的适配器，直接使用 |
| 单侧（SAC 加 PID） | 虚拟的驱动和转向 | 经过车辆适配器换成油门和舵机，转向只取反一次 |
| 停车 | 自带有符号的电调输出，可以倒车 | 转向从 0 开始，接管后 0.5 s 内限速，与它在实车上单独测过的方式一致 |

整个节点只有一个发布者。停车的优先级最高，一旦接管就锁定；交接的那一帧，驱动和转向都归零；完成（DONE）和中止（ABORT）之后都保持零输出。外部的使能、零输出和看门狗保持原样，策略自己从不使能车辆。停车期间，前进方向的道路观测暂停，绝不拿倒车以前的旧路线去喂 SAC。

这些规定来自一次教训。第一版集成链把一个 MPC 双侧控制器、SAC 单侧控制器、停车模块和一个基线接在一起，当时共享的只有观测。后来做了一个独立的回退实验：SAC 失败时，改由 MPC 接管。结果在 430 次仿真任务里，完成的只有 67 次，尽管接管发生了 46 次。光有一个“备用”是不够的。共享观测只是起点，动作的单位、检查的宽度、丢路时的处理也要对齐，控制器之间才谈得上互换。后续的工作做的就是这些：对齐动作单位，对齐绕障规则和最后一道检查的宽度（早期的 0.33 m 和最终的 0.45 m，对同一个缝隙给出了相反的结论，见[第一篇](/projects/obs18-memory-and-safety)），以及丢路时的交接。

## 触发方式：什么时候算一步

每个模块在车上单独验证时，触发方式并不一样。集成以后要统一成一个节拍，这就带来新的差异。

| 模块 | 车上单独验证时的触发方式 | 整条链里的做法 |
| --- | --- | --- |
| 双侧 PPO | 每个相机帧（约 10 Hz） | 整个节点每个雷达帧运行一步。PPO 仍只在有新的相机帧时更新，其余时间保持上一条命令，所以最多比单独运行时晚约 0.1 s 拿到相机帧 |
| 单侧 SAC 加 PID | 固定的 10 Hz 定时器 | 随雷达帧触发（车上雷达帧的间隔，中位数是 0.100 s）。这是唯一一处没有在实车上验证过的触发变化 |
| 停车 | 雷达帧 | 随雷达帧触发，与车上测试一致 |

整条链选用雷达帧作为节拍，依据是一组停车仿真：参数随机化，车后方有盲区，每格 30 个随机种子，只测停车。表里的软管车位，是用软管围成的 U 形车位（内尺寸 1.2 × 0.45 m）；白板车位，是用薄白板围成的车位（内尺寸 1.6 × 0.40 m）。

| 车位 | 雷达帧触发（实车测试的方式） | 定时器，最坏情形（雷达帧总是晚 0.1 s） | 最坏情形再加 10% 漏帧 |
| --- | --- | --- | --- |
| 软管 1.2 × 0.45 m | 29/30，无碰撞 | 25/30，2 次碰撞 | 28/30，无碰撞 |
| 白板 1.6 × 0.40 m | 11/30，无碰撞 | 7/30，无碰撞 | 10/30，无碰撞 |

两种车位下，雷达帧触发的结果都最好，所以整条链采用雷达帧触发。每一格只有 30 个随机种子，差别不大，这组数据只能作为选择的依据，不能说明差异显著。白板车位在仿真里本来就比较弱，失败多半是因为修正次数超过了上限。

## 先隔离，再整链：用开环回放证明“一致”

节点启动时有一个模式参数 `integration_mode`，用来把各个模块隔离开，一次只测一个。

| 值 | 行为 |
| --- | --- |
| `chain` | 完整的链，可用时带备用基线，默认执行完整的停车 |
| `single` | 只跑 SAC 加 PID，不自动切停车，也不自动用基线，用来单独测稳定性 |
| `double` | 只测 PPO，不自动切单侧或停车 |
| `parking` | 只停车，从第一帧起自己找车位 |
| `baseline` | 只测备用基线，仍然检查它的适用范围 |

每个模块先单独测，再整链测。整链里最有价值的一件事，是证明每个模块与“上车跑过的那份代码”逐帧一致。办法就是开环回放：把实车记录下来的输入逐帧交给集成后的代码，再把输出和实车上那份代码的输出比较。

- 双侧 PPO：五次实车运行共 1,610 个相机帧，回放得到的输出与实车节点的代码逐帧完全相同，最大差为 0.0。
- 停车：17 次只停车的实车运行共 3,340 个雷达帧，同样完全相同。规划用的是固定的时间片，所以结果不受 CPU 快慢影响。
- 其中一段（150 帧，含一次绕板；284 帧，含倒车）被固定下来，作为回归测试。
- 整条链在笔记本上每个周期约 3.4 ms（车上约慢 4 倍），远小于 100 ms。实车上一步的中位数是 49 ms，最大 131 ms。
- 所有代码、固定参数和网络权重都放在一个节点文件里，车上只需要 ROS 的依赖和 NumPy，不依赖训练目录或模型服务。

开环回放能说明什么，不能说明什么？它说明：同样的输入，集成后的代码给出的输出，与车上测过的代码相同。它不说明整条链在车上闭环运行时一定稳定，因为闭环里输出会影响下一帧的输入，节拍上的细小差别（比如上一节讲的触发方式）也可能带来影响。

上车测试的顺序，在文档里是这样规定的，每一步只换策略的配置文件，重新构建并重启，行驶中不改硬件配置：

1. 只测停车；
2. 只测双侧；
3. 只测单侧；
4. 整条链，但停车接管以后输出归零；
5. 整条链，完整执行停车。

## 让当前状态看得见

现场最怕的是不知道“它现在到底在用哪个控制器”。节点把当前使用者的编号放进调试话题 debug1：

| debug1 | 含义 |
| --- | --- |
| 0 | 停止：输入或路线不适用 |
| 1 | 双侧 PPO |
| 2 | 单侧（SAC 加 PID） |
| 3 | 停车 |
| 4 | 备用基线 |
| 5 | 停车完成 |
| 6 | 停车中止 |

每次切换，还会打印一条带原因和最近事件的 INTEGRATION 日志。需要注意，可视化工具 Foxglove 里的 `policy_fsm_state_value = 3` 只表示“策略正在计算”，并不表示正在停车，单看它分不出当前是谁在开。

备用基线是一个简单的备用控制器，没有激光绕障能力，所以接管的条件很严：只有当前任务适用的候选拿不出有效动作，或者在确认可走的路上停了 3 s 且不是有意的停，才轮到它。路线未知、激光未知、前向不明、路内有障碍、停车已锁定时，它都不适用，并且记录拒绝的原因。

## 一次完整的运行

下面是一次用这条链从头跑到尾的实车运行（手机视频，加上链的事件列表）：

- 0 到 23.0 s：PPO 在双侧路上开了 10.3 m，平均 0.45 m/s，弯道里用到了整个 ±1.0 的转向范围。
- 21 到 23 s：一条锥桶线结束，单侧证据累计到 1 m，23.0 s 切到单侧控制器。
- 23.0 到 26.0 s：单侧控制器开过单侧的弯，航向约转了 100°，角速度最大约 1.4 rad/s。
- 26.0 到 26.9 s：共享观测里没有路了，链先停车；路断 1 s 之后，停车模块接管，从原地开始找车位。
- 63.8 s：停进软管车位，状态为 DONE，距离交接过去 37 s。

## 容易出错的地方

| 容易有的想法 | 实际情况 |
| --- | --- |
| 各个控制器单独都好用，拼起来就能用 | 回退实验里接管发生了 46 次，430 次任务仍只完成 67 次。单位、检查宽度、丢路时的处理都要对齐 |
| 只看到一条线，就说明另一条线不存在 | 弯道和绕板时，另一条线只是在视野之外。直接判断，误判最长连续 11.3 m；用证据判据，最长只有 0.7 m |
| 一有新的证据就切换，反应最快 | 示意图里，每帧都切换要切 14 次，用迟滞只切 2 次 |
| 回放输出完全一致，上车就没有问题 | 开环回放不包含闭环的影响。单侧控制器改用雷达帧触发，就是一处没有在实车上验证过的变化 |
| 视野里一时没有锥桶，就是出错了 | 这是预期的行为：连续 1 s 没有锥桶，停车模块会试探着接管，看到锥桶后再退回。实车日志的 64 次里，有 3 次中途丢了 4 到 9 s 的锥桶 |

## 适用范围和局限

- 单侧绕过板子以后，重新接回道路仍然不稳。另一份诊断日志重查时，候选的路线常常只有 0.2 到 0.4 m，随后混入另一种颜色的锥桶，偏离约 0.85 m 以上，远段的起点超出了近端外推的范围。针对这一点加入了“有证据的重接”：3 个不同的相机帧里，两个有限的锚点位置和方向一致，才换路线。但是没有原始的完整激光数据，所以那次检查不是动态回放，也不是碰撞验证，不能说已经凭这项修改跑通。
- 闭环仿真的记录要如实地读。最终的 42 个已完成回合里，单侧绕板 3/3 完成，强制向前的错误被保护拦停 3/3；但整条链里仍有 PPO 阶段的超时和停车中止，所以“42 个跑完了”不等于“42 个成功”。
- 倒车模型是依据日志估计的假设，不能代替实车验收。
- 停车期间，前进方向的道路观测是暂停的。如果将来需要停车之后继续行驶，要另外做重新建路和接管，当前版本不包含。

## 小结

> 板书
>
> - 用“看到什么”选控制器，不用里程和路段长度
> - 用证据，不用计数；进和出的门槛不同，这就是迟滞
> - 不在场的控制器保持热备，切换时从当前的转向接续
> - 共享观测只是起点；单位、检查宽度、丢路处理要一起对齐，发布者只有一个
> - 先单独测，再整链测；用开环回放证明与车上的代码一致，再看闭环里还有什么没验证

## 思考题

1. 为什么进入单侧控制要累计 1 m 的证据，而回到双侧控制只要连续 3 帧？（提示：一个是推断，一个是直接观察。）
2. 车以 0.45 m/s 行驶，累计 1 m 的证据大约需要多长时间？（参考答案：1 ÷ 0.45 ≈ 2.2 s。）
3. 如果取消热备，切换回双侧的那一刻，PPO 的哪些内部状态是过时的？可能带来什么后果？
